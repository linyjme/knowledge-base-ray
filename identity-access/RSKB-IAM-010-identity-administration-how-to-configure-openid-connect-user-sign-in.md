# Identity administration: how to configure OpenID Connect user sign-in

## Short answer

An administrator must first create a client for RaySync user sign-in at the identity provider, then enter the corresponding OIDC information displayed by both sides. The sign-in redirect URI must match exactly on both sides. After saving, use the test link generated by the page to verify the complete sign-in flow.

## Prerequisites

This applies to version 8.1.8.7 environments with OpenID Connect functionality and an OIDC-compatible organizational identity provider. Product administrator permission and identity-provider client configuration permission are required. Prepare a dedicated regular test account.

Only an authorized administrator may make this change. Use organization-approved values and confirm that the exact target is **configure OpenID Connect user sign-in** in the intended deployment, edition, and component.

## Effect

An administrator must first create a client for RaySync user sign-in at the identity provider, then enter the corresponding OIDC information displayed by both sides. The sign-in redirect URI must match exactly on both sides. After saving, use the test link generated by the page to verify the complete sign-in flow.

The change affects only the confirmed target and documented scope. It must not be treated as authorization to alter a different account, rule, service, license, user, or external system.

## Confirmation

Before execution, record the current state and confirm the exact target, intended effect, affected users, maintenance window where relevant, and a valid post-change check. Never copy credentials, activation codes, verification codes, or private addresses into documentation or support notes.

## Procedure

1. Create a client at the identity provider and confirm that it allows the sign-in redirect URI required by the product page.
2. Go to “User Integration > Sign-in Authentication > OpenID Connect” and enter the name, issuer URL, client ID, and client credentials.
3. Enter the authorization endpoint, token endpoint, user information endpoint, and scopes supplied by the identity provider. The logout address is optional and depends on the page and provider requirements.
4. Enter a “Sign-in Redirect URI” exactly matching the value registered at the identity provider. Protocol, host name, port, path, and trailing slash can all affect matching.
5. Save the configuration. After saving succeeds, open the displayed “Test Link,” sign in with a regular account, and confirm that it returns to the product.
6. After testing succeeds, enable the method, configure the default user role, and evaluate whether to make it the default authentication method.

## Recovery boundary

First verify that the sign-in redirect URI, issuer URL, client ID, endpoints, and scopes match exactly, and that the test account is active at the identity provider. For redirect loops, rejected redirects, or inability to retrieve user information, also check browser time, product and identity-provider time, and network connectivity.

If the result differs from the confirmed effect, stop. Restore the recorded prior values only when the interface and external provider support that rollback. A sent message, deleted rule, restarted service, synchronized identity, or consumed activation operation cannot be automatically recalled; use the documented product or provider recovery path.

## Verification

The configuration saves successfully and displays a test link. The test user is redirected to the identity provider, returns to the product after authentication, and receives the administrator’s preset product permissions.

Verify the exact target after the operation and retain only a non-sensitive result, time, and visible status. If the identity-provider client or organizational claim mapping must change, or testing repeatedly fails, contact the product and identity administrators. Provide the product version, failure stage, test time, identity-provider name, and redacted visible error. Do not send client credentials or user tokens.

Keep the scope explicit: a user account, group, role, space, policy, and storage allocation are distinct objects. A change or entitlement in one scope must not be assumed for another.
